Start Here

Corbanu Terminal is a product fork of OpenAI Codex CLI. The repo keeps the Codex execution engine, tool loop, approvals, sandboxing, sessions, and app-server mechanics, then layers Corbanu/PFTerminal product surfaces on top: providers, model picker, vault, wallet, GPU routes, Task Node, Telegram, panes, and managed multi-agent orchestration.

The mental model

Treat this as a terminal-native AI trading and engineering command center. It is not a generic web assistant or a thin rebrand. The product contract is preserved through working commands, exact provider/model identity, credential containment, visible panes, and evidence-based completion.

Begin with the living product spec: docs/pfterminal-spec.md.

The active spine

The active release and security work are tracked under docs/current-sprint/index.md. The current security workstream is narrow but important: agents and panes must use provider credentials without seeing or inheriting raw long-lived secrets.

Development Workflow

The working session converged on a document-driven development loop. The plan says what should exist. A sprint translates one feature into mechanical execution. TUI proof and human acceptance decide whether the work is actually done.

1. Product plan Describe the pain, user behavior, product contract, and code references.
2. Sprint One feature only. Tight implementation steps, not flowing prose.
3. Build Make scoped code changes in the owning modules.
4. TUI proof Run the actual terminal workflow, preferably in tmux/panes.
5. Acceptance Human confirms the feature works; docs/evidence record the result.

Plans vs sprints

A plan can be broad and strategic. A sprint should be narrow, executable, and mapped to exactly one feature. The agreed direction is to add a dedicated sprint workflow so future agents work from concrete implementation contracts instead of oversized prose plans.

Useful existing anchors: current sprint index and 0.1.27 convergence spec.

Interactive proof matters

A recurring failure mode is agents using non-interactive shell execution and then claiming a TUI workflow works. For terminal features, proof should exercise the real TUI: launch it, navigate it, create panes or agents if relevant, and capture evidence before marking work complete.

See feature evidence such as spawn acceptance.

Working in tmux

The working-session shorthand was: inspect sessions with tmux ls, attach with tmux attach -t <name>, and detach with the tmux prefix then d (usually Ctrl-b, then d; some setups use Ctrl-a). Use tmux when coordinating Corbanu, docs, and agent panes side by side.

Development Conventions

The repo-level AGENTS.md is authoritative. This section is the condensed version most useful while editing.

Rust workflow

  • In codex-rs/, crate names are prefixed with codex-.
  • Use just test -p <crate>; do not run cargo test directly.
  • Run just fmt after code changes anywhere in the Rust repo.
  • Before finalizing larger Rust changes, run just fix -p <crate>.
  • If dependencies change, run just bazel-lock-update from the repo root.
  • If config schema types change, run just write-config-schema.
  • For app-server API shape changes, run just write-app-server-schema and just test -p codex-app-server-protocol.

Code style

  • Collapse nested if statements when Clippy would ask for it.
  • Inline format! arguments when possible: format!("hello {name}").
  • Prefer method references over redundant closures.
  • Prefer exhaustive match arms over wildcard arms where practical.
  • Avoid ambiguous bool or Option positional arguments; use clearer API shapes or exact argument comments.
  • New traits need doc comments and should prefer native RPITIT future returns over async_trait.

Architecture discipline

  • Resist adding new concepts to codex-core; look for a better crate first.
  • Keep crate API surfaces small and prefer private modules with explicit public exports.
  • Avoid growing already-large TUI files; add focused modules for new behavior.
  • For MCP tool-call mutation, prefer codex-rs/codex-mcp/src/mcp_connection_manager.rs.
  • Do not call reset_client_session unless the incremental-check logic really requires it.

Testing discipline

  • Agent logic changes need integration tests, preferably under core/suite using test_codex.
  • UI changes need insta snapshot coverage and accepted snapshots.
  • Use pretty_assertions::assert_eq and compare whole objects when possible.
  • Do not mutate process environment in tests when a passed dependency or flag will do.
  • For first-party binaries in tests, prefer codex_utils_cargo_bin::cargo_bin.
Security guardrail: do not add or modify code related to CODEX_SANDBOX_NETWORK_DISABLED_ENV_VAR or CODEX_SANDBOX_ENV_VAR. The repo already uses those boundaries deliberately for sandbox-aware tests and execution.

What We Agreed To Build Next

The working session produced two layers of next work: immediate security/process work and later product expansion. The immediate work should be converted into proposed plans and then one-feature sprints.

Security profiles /security permissive, moderate, and aggressive should be explicit modes, visible in the UX, and recorded in logs for later audit.
Secretless agents Agents ask to use capabilities; Corbanu resolves vault credentials outside model context and never passes raw long-lived keys to shell-capable panes.
Brokered leases A local lease broker gives panes short-lived scoped access to provider calls while keeping real provider keys inside the runtime boundary.
Prompt firewall External text is treated as untrusted, cleaned, labeled by source, and optionally classified for hostile prompt-injection content before reaching the agent.
Sandboxed web Browser/search interactions should be isolated through controlled providers or a sandboxed browser path such as Scrapling-style retrieval, not raw agent browser access.
Regression harness Seed synthetic hostile data, fake secrets, and suspicious trading prompts, then prove transcripts, artifacts, logs, and tool outputs stay clean.

Immediate plan candidates

Plan Build intent Likely starting references
Security mode UX and logging Add or formalize permissive/moderate/aggressive security modes, make the current mode prominent, and inject it into logs/audit records. agent vault access, codex-rs/tui/, codex-rs/config/
Provider capability registry Represent provider capability, vault label, transport, billing, and allowed use as typed data instead of prompt instructions or env-var folklore. model-provider-info, models.json, provider_key_vault.rs
Vault lease broker Let Claude panes/subagents use provider routes without inheriting raw keys. The model sees a lease token and local broker URL, not a provider secret. vault, secrets, app-server, Claude panes
Prompt-injection firewall Clean and label untrusted external text before it enters model context; evaluate lightweight classifiers or deterministic cleaning rules for hostile trading prompts. core/src, context-fragments, sandbox docs
Web/search isolation Route web retrieval through explicit search/browser providers and a sandboxed browser pattern instead of letting agents directly operate an untrusted browser surface. core tools, codex-mcp, security sprint
Sprint documents Create a clear sprint contract: one sprint per feature, mechanical execution steps, evidence slots, and completion/cleanup rules. current-sprint, features, TBD

Product expansion ideas captured for later

  • Bundle useful market data with paid plans: Tiingo, Sharadar, and internally built Hyperliquid data feeds were discussed.
  • Consider plan add-ons or marketplace purchases for data feeds and other agent capabilities.
  • Add first-class integrations with brokerage agent services such as Robinhood and Interactive Brokers where they make sense.
  • Explore a wallet-linked public chat or Trollbox style surface, likely tied to PostFiat/Nostr identity primitives.
  • Integrate PostFiat/NAB portfolio publishing concepts as a later product surface.
  • Keep provider supply flexible: Ambient, Z.AI, OpenRouter, Akash, BitTensor-style routes, and other sources should be evaluated by quality, cost, privacy, and crypto-native payment fit.
Important product tradeoff: privacy and broad provider supply can pull in opposite directions. A Corbanu-operated provider router may improve supply and billing, but it changes the privacy story. Treat that as an explicit product decision, not an accidental implementation detail.
