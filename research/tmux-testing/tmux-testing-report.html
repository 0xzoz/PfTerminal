Testing Codex effectively with tmux

A practical strategy for turning ad hoc terminal QA into a reliable, artifact-rich test layer for Codex, PFTerminal, and other Ratatui-based flows.

Executive Recommendation

Codex should use tmux as the system-level TUI test substrate, but not as the only test substrate. The strongest approach is a four-layer test stack: widget snapshots, PTY process tests, tmux viewport tests, and release-grade tmux matrices.

1
Build a first-class Rust tmux driver instead of growing more shell helpers.
2
Keep captures small, named, and viewport-aware; store full scrollback only on failure.
3
Use tmux control mode for event streams, pane identity, resize fidelity, and future multi-pane orchestration tests.
Bottom line: tmux is most valuable where ordinary unit tests lie: real resize/reflow, key translation, paste semantics, scrollback, alternate screen behavior, multi-pane dispatch, process cleanup, and transcript-visible state. Keep deterministic Ratatui snapshots for pure rendering and use tmux for end-to-end behavior.

Why tmux Fits Codex

The Codex repository already has three important ingredients. First, it has many Ratatui snapshot tests for deterministic UI components. Second, codex-utils-pty exposes a reusable PTY abstraction with stdin, resize, exit, and output streams. Third, there is live tmux QA history in qa/orchestrate_tui_matrix.sh and ignored smoke tests under codex-rs/tui/tests/suite/resize_reflow.rs.

tmux adds a real multiplexer and terminal viewport around the app. The tmux manual describes sessions as collections of pseudo terminals with windows and panes, managed by a server process; this maps directly onto Codex's multi-pane and long-running task model. The command-line API gives Codex a way to create sessions, send keys, resize panes, capture the viewport, and kill the isolated server.

Recommended Test Architecture

The driver should live close to TUI integration tests, probably as a test-support module before it becomes a crate. It should expose TmuxServer, TmuxSession, and TmuxPane types with methods like send_literal, send_key, capture_viewport, capture_scrollback_tail, resize_client, split, wait_until, wait_stable, and artifact.

Research Findings

Finding Evidence Implication for Codex
tmux is scriptable enough to behave like a terminal Selenium layer. David MacIver's tmux testing writeup identifies the primitives: unique server, detached session, capture current pane, send keys, and kill server. Codex should formalize these primitives rather than rely on one-off shell scripts.
Control mode is the right upgrade path for precise automation. The tmux wiki says control mode is text-only, parseable over SSH, returns command blocks, emits pane output notifications, and recommends IDs and formatted output. Use shell commands for simple viewport tests; use control mode for multi-pane state, flow control, and event ordering.
Screen snapshots are appropriate but insufficient. Ratatui's testing guide recommends fixed terminal sizes and snapshot review. Waleed Khan argues snapshots fit TUIs because many UI requirements are hard to express with ordinary assertions. Keep snapshots for widgets and use tmux for full process behavior, key routing, scrollback, and resize.
TUI automation needs stability, not just sleeps. Recent TUI testing research describes harnesses that wait for rendered grids to stabilize after each action and then record character-grid state. Replace fixed sleeps with bounded polling plus stable-grid heuristics and failure artifacts.
Codex already has live tmux patterns worth preserving. qa/orchestrate_tui_matrix.sh isolates homes, starts fixed-size sessions, polls only the live viewport, records captures, and snapshots layout JSON. Port the proven release-QA rules into reusable Rust support and keep the matrix as a high-level scenario layer.

Harness Design

Session isolation

Every test should use a unique tmux socket name, session name, temporary CODEX_HOME, temporary workspace, and deterministic mocked model provider. Prefer tmux -L codex-test-$PID-$RANDOM or an explicit socket path so the test never touches the developer's default tmux server.

tmux -L "$socket" new-session -d -P -F '#{pane_id}' \
  -x 120 -y 40 -s "$session" -- \
  env CODEX_HOME="$home" OPENAI_API_KEY=dummy \
  "$codex" -c analytics.enabled=false -c "$mock_provider" --no-alt-screen -C "$repo" "$prompt"

Viewport assertions

Assert against the live viewport by default. The existing matrix correctly avoids searching scrollback while waiting for dialogs because stale titles can satisfy a wait and send subsequent keys to the wrong surface. Full scrollback should be captured on timeout and as a named artifact, not used casually as the synchronization oracle.

Control-mode assertions

Use tmux -C or tmux -CC when tests need pane identity, output notifications, layout changes, or precise command boundaries. Parse %begin/%end/%error blocks, %output, %layout-change, %pane-mode-changed, %pause, and %continue. For command inspection, prefer -F formats and pane IDs over names or indexes.

Artifact contract

Each failure should emit a compact bundle: viewport capture, last N scrollback lines, tmux pane metadata from list-panes -F, tmux server/client logs when enabled, Codex logs, mock-provider transcript, test config, terminal size history, and a one-line reproduction command.

What to Test With tmux

Workflow Primary assertions Why tmux matters
Startup and trust prompt Prompt appears, Enter accepts, model/status line renders, composer is focused. Exercises real initial terminal mode and first input routing.
Slash commands and pickers One Enter dispatches, filter matches visible rows, Esc returns to composer, queued text survives. Matches historical failures around sticky slash commands and picker routing.
Resize and split-pane reflow Composer row and sentinel content remain anchored across vertical split, horizontal split, close, and repeated resize cycles. Only a real terminal multiplexer reliably exposes viewport reflow bugs.
Long-running turn interruption Esc, Ctrl-C, approvals, and background tasks leave no hung turn and no lost prompt. End-to-end event handling and process state are hard to model with unit tests.
Multi-pane orchestration Targeted task goes only to selected child; report returns to intended parent; Main remains responsive. This is where tmux release QA already found high-impact routing defects.
Terminal-specific features Shift-Enter, modifyOtherKeys, clipboard fallback, OSC/tmux passthrough, image disabling inside tmux. Codex contains tmux-specific behavior that should be tested under tmux, not only by mocked env vars.

Implementation Plan

Phase A: Extract

Move common tmux helpers from shell/Rust smoke tests into codex-rs/tui/tests/support/tmux.rs. Keep it Unix-only, skip gracefully when tmux is missing, and make every command report stdout/stderr on failure.

Phase B: Stabilize

Add stable-grid waits, named captures, panic-safe cleanup, unique sockets, and a fixed artifact schema. Convert one ignored resize smoke into a fast, deterministic ignored-by-default test that is trivial to run locally.

Phase C: Gate

Add a tiny CI smoke lane on Linux with tmux installed: startup, one slash command, one resize, one clean exit. Keep longer orchestration matrices manual or nightly until flake rate is measured.

Most important local evidence:

  • codex-rs/tui/tests/suite/resize_reflow.rs has ignored tmux smoke tests for split and width resize behavior, using mocked SSE responses and temporary homes.
  • codex-rs/utils/pty/README.md documents the reusable PTY process abstraction that should remain the lower-level companion to tmux tests.
  • qa/evidence_20260703/status/tui_qa_findings.md shows real tmux-driven QA caught routing, child-report, responsiveness, and slash-command issues that ordinary snapshots would likely miss.

Decision Matrix

Do not make tmux carry everything. The durable pattern is to choose the cheapest layer that can actually observe the bug class. Rendering defects belong in snapshots. Process IO belongs in PTY tests. Multiplexer and viewport behavior belongs in tmux. Long, cross-feature release qualification belongs in the matrix.
