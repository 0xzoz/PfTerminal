4. Merge and CI rules

  • Merge commits only: gh pr merge N --merge --match-head-commit <sha>, only when all checks are green and none pending. Never force-push. Never rm -f (use rm -r … < /dev/null). Never pkill broadly.
  • Don't merge a worker's PR while the worker is still running (it may still be fixing review items). Coordinator merges are OK when the worker has finished, or for docs-only PRs whose author is idle.
  • Security sign-off: any change that alters Permissive behaviour (beyond owner-decided items) or the sandbox boundary in a new way must stop at an open PR titled “— needs security sign-off” for Travis.
  • Watch GitHub closing keywords in PR bodies (#433 once auto-closed #431). Use “Refs #N” when the PR must not close it.
  • main has no “branch must be up to date” rule. Merge origin/main into a PR only when it's conflicting, when it depends on newly merged code, or when a failure was fixed on main. Every push restarts ~40 CI jobs; needless re-merges were the main CI bottleneck on 2026-10-12.
  • CI structure: PR CI (rust-ci, core security tests on Linux+macOS added by #517/#556, tmux smoke, credential canaries on 3 OSes, build/package, blob size policy, repo checks); postmerge-ci on main (rust-ci-full incl. Windows clippy and full Linux test shards); nightly-ci (heavier jobs, incl. codex-core with developer-accounting since #567). CodeQL runs only on main/nightly — ignore stale CodeQL checks on PRs. A Cargo profile change triggers the v8-canary Bazel builds (~3 h).
  • PR CI has no Windows clippy (only postmerge rust-ci-full): for changes touching platform-gated code, dispatch gh workflow run rust-ci-full.yml --ref <branch> before merging (see section 10).
  • Pushing workflow changes: follow the pushing-ci-changes skill.
