Fixes #466. Bounded fix. Product spec: "Shipping MVP — LIVE", Workspaces row: "`/panes`, `/agent`, approvals, existing general sandboxing". This restores the end of an approved command's cell and changes no permission.

**What #466 saw and what was left.**
- The approval prompt shows its command as running. The app server starts the command item when it asks, so the item must later be ended by Core.
- #466 saw an approved command that the sandbox stopped at start (`echo hacked >> ../outside-notes.txt` under Aggressive) stay "◦ Running". The #443 follow-up (492a40066b, merged after #466 was filed) already ends that case. On current main, in tmux with GLM 5.3 Flash, the approved `echo >> ../outside-notes.txt` and the approved `curl` both show "• Ran".
- What remained is the same symptom by another route. A command the person **approved** that then fails to start for any reason other than a sandbox denial still returned without an end event and stayed "◦ Running" for good.
- Reproduced on main in tmux:
  - Permissive with `secretless_agent_launch`; the model runs `touch ../escalated.txt` with escalated permissions; approve.
  - The protected launch refuses it ("this command would run outside the OS sandbox"), and the cell stays "◦ Running touch ../escalated.txt" after the turn ends.

**Fix.**
- `UnifiedExecRuntime` records whether the last *command* approval prompt was approved. Network prompts don't start an item, so they are not counted.
- When such a command fails before it starts, `exec_command` emits its begin event (the app server de-duplicates it with the prompt's start) and a failed end event that carries the reason.
- A declined prompt is still ended by its owner (the app server) and gets nothing more. A cached approval showed no prompt, so nothing changes there.

- `issue_466_a_declined_command_gets_no_second_end`: after a decline, Core emits no begin/end.
