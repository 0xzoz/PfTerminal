## How this PR and #585 interact

**Hidden default login and the new account-following code.**
- `ActiveAuthManager::for_provider` and `follow_provider` start from `default_account_manager()`. In a process that hides the default login, that is the base manager built by `shared_from_config`, so it has the hide flag and a cached `auth` of `None`.
- `AccountModelsManager.default_auth` comes from the same base through `build_models_manager`. The PR's `shared_from_config` call sites are unchanged.
- Named managers made from that base get `hide=false` and the configured `forced_login_method`. Their own sign-in checks therefore use the configured restriction, as #571 intends.

**Nothing sends a request with a hidden login.**
- Model requests: after a switch, `build_model_client_for_configuration` uses the active (default) manager. `auth_manager_for_provider` then returns `default_account_manager()`, and `api_auth` refuses with `hidden_default_login_reason()` before any request is sent.
- The `ModelClient::for_provider` path, coming from a named manager, also falls back to the base.
- Connectors, plugin installs, MCP prewarm, tool suggestions and the OpenAI file rewrite all read `active_auth` and get `None`.
- Accounting (`accounting_auth_mode`) gets `None`.
- `/apps` and rate limits use `shared_from_config` after the process-wide flag is set, so they are hidden too.

**Model list after a switch to the default login.** `follow_sign_in_account(None)` rebuilds the list with the hidden base. `refresh_available_models` only fetches when `uses_codex_backend` or command auth applies, and both are false with no auth. So `/models` is never requested without credentials. The TUI refetch just returns the cached or bundled list.

**No wrong refusals.**
- `default_login_restriction_error` and the `api_auth` refusal both apply only to OpenAI-auth providers with no `env_key`, `auth`, `aws` or account.
- Z.AI and other providers, and named-account threads, are not affected.
- Hiding uses the configured `forced_login_method`, so the API-key-only default implied by a Z.AI session does not hide a ChatGPT default login in a resume launch.

**"Use default account for this session"** still starts a fresh thread, so it is still refused at thread start with the reason, matching the `switchdef` capture. A mid-session provider switch (the new #585 path) is refused at the first request instead, with the same reason.

**`provider_status_host` OpenAI status.** `discover()` builds its manager through `shared_from_config`, so in a hiding process a ruled-out default login shows as Missing. The host is rebuilt from the current config when `/providers` opens, so the named-account entries follow switches.

## Findings (all P3, none blocking)

1. **The refusal reason can go stale until restart.** The hidden reason is only recalculated on `load_auth`, i.e. at construction, on `reload()` or after an in-process login through the app server's `account/*` methods. Thread start and `api_auth` don't reload. If the user follows the message's own advice and runs `corbanu login` in another terminal, the running process keeps refusing with the old reason. Possible fix: call `reload()` on the default manager before refusing.

2. **The #585 switch message is misleading in a hiding process.** After a `/model` switch to an OpenAI-auth provider with no named account (for example after `corbanu resume` of a Z.AI thread), the TUI says "Connectors, usage and the model list now use the default account; model list refreshed." The default login is actually hidden, and the next turn fails with the reason. Possible fix: add the hidden reason to the message.

3. **Doc comment wording.** The comment on `default_login_restriction_error` lists "switching to the default account" as a thread-start case. Since #585, a mid-session provider switch is refused at the request instead; only "Use default account" goes through thread start. Worth a wording tweak.

4. **Cosmetic, pre-existing.**
   - In a hiding process, the refreshed default model list can come from a `models_cache.json` fetched earlier with the now-ruled-out login. It only affects what is displayed.
   - The cloud-config bundle loader (`AuthManager::shared`) doesn't hide; it runs during config load, before this PR's checks, so this PR doesn't change it.
