**Verdict: request changes.** One blocking problem: a test in `codex-core` should now fail. The round-2 nits are fixed, and resume and fork on the embedded app server are correct. I didn't build or run anything, so the failing test is from reading the code.

## Blocking

**1. A thread-start test should now fail** (`core/src/thread_manager_tests.rs:524-538`).
- **Cause:** `default_login_restriction_error` (`core/src/config/provider_accounts.rs:228-247`) now returns the default-login manager's hidden reason without looking at the thread config's restrictions. The removed storage check used to do that.
- **Failing case:** `(&unrestricted, &hiding)`. `unrestricted` passes every gate: the feature is on, it uses the OpenAI provider, and it has no account, `env_key`, `auth` or AWS. `hiding` still holds a reason, because it was built from a config with `forced_login_method = chatgpt` and an API-key login. The call returns `Some(reason)` while the test asserts `None`.
- **Which behaviour is right:** the new behaviour. The hiding is set for the whole process, and the provider (`provider.rs:561-575`) refuses requests with that reason whatever the thread config says, so refusing at thread start is consistent.
- **Fix:** change the test, not the code. Replace that case with a manager that hides but has no reason, such as `shared_from_config` from a named config with no restriction. Then run `just test -p codex-core` (and the login crate) before handoff. Nothing I found records a test run for this commit.

## Should-fix

**2. With a reused local daemon, `--account` sessions log the default login out again** (`tui/src/lib.rs:1401-1412`).
- **What changed:** the `Embedded` gate covers `runs_on_named_sign_in_account()` as well as resume and fork. So `corbanu --account work` against a running daemon on macOS/Linux enforces at startup and deletes a ruled-out default login. That is the original #570 behaviour.
- **Why it happens:** `--account` is a typed override, not a key/value override, so it doesn't stop the daemon from being reused. A named account set in `config.toml` has the same effect.
- **Context:** round 2 left the login alone on this path; `main` behaves the same as this commit. Choosing to enforce is defensible: it is the safer choice for an admin policy.
- **Conflicts in the docs and demo:**
  - `docs/provider-accounts.md:147-149` says a named-account session "leaves the default login alone even when they rule it out". The daemon sentence at `:153-154` sits in the resume/fork part of the paragraph and doesn't clearly cover `--account` sessions.
  - The demo spec claims "a named-account session never logs out the default login". It only ever runs embedded: its `-c` overrides prevent daemon reuse.
- **Fix:** state the daemon exception for named sessions in the docs and the demo/QA record, and file a follow-up. The real fix is daemon-side hiding: have the app server call `leave_default_login_unenforced()` when `named_accounts` is on. That needs a product decision.

## Nits

- **External auth set after startup leaves an old reason** (`login/src/auth/manager.rs:3204-3212`, `:3650-3669`). `set_external_auth` → `commit_external_auth` caches valid external tokens but doesn't clear `hidden_default_login_reason`. Because the thread-start check no longer looks at the cached auth, a default thread is then refused even though requests would succeed. The provider guard does check `auth.is_none()`, so requests themselves are fine. This only happens when a client uses `chatgptAuthTokens` in a process that hides; the TUI and `exec` don't. Fix: clear the reason in `commit_external_auth`, or have the check also require `auth_cached().is_none()`.
- **The reason only updates on reload.** If someone signs in with `corbanu login` in another terminal, the reason (and the cached `None` auth) stay until a reload, so a later switch to the default login gets the old "sign in with `corbanu login`" message. Requests behave the same way, so this isn't a regression. Optional fix: when a reason is set, reload the default manager before refusing. That only costs a read on the refusal path.
- **Doc comment** (`provider_accounts.rs:220-227`): "while that login breaks the configured login restrictions" should say it is the process's restrictions, as captured by the manager, not the thread config's. This ties in with item 1.
