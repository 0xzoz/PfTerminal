## Should-fix

**1. `corbanu fork` of a named thread still ends at the default sign-in screen (medium).**
- **Why:** `tui/src/lib.rs:1660-1663` excludes fork from the early `#545` selection.
- **What happens:** with the default login hidden, `requires_provider_onboarding` is true. With `forced_login_method=chatgpt`, `default_login_forced_method(initial_config)` also returns `Chatgpt` (`lib.rs:~1726`), because the recorded account isn't known yet.
- **Effect:** the user has to sign in to the default ChatGPT login, which overwrites the API key they kept, or quit.
- **Docs:** `docs/provider-accounts.md:149` says `fork` leaves the default login alone. That's true at startup, but the user can't reach the forked thread without replacing it.
- **Fix:** extend the early selection to forks, or narrow the docs and record a follow-up.

**2. A TUI that reuses the local daemon (macOS/Linux) loses the protection round 1 had (medium-high).**
- **Setup:** `corbanu resume …` or `--account …`. The implicit daemon is reused (`app_server_target_for_launch`, `lib.rs:981-997`), because `--account` doesn't count as a non-replayable override.
- **What happens:**
  - The flag is set only in the TUI process, which also no longer enforces.
  - The daemon is a separate process. Its managers don't hide, so `hides_restricted_default_login()` is false there and the check at `provider_accounts.rs:231-234` is skipped.
  - A default thread in that daemon (a resumed default thread, a `/providers` switch, a spawned agent) therefore runs on the ruled-out login.
- **Compared with main:** main deleted the login from storage at TUI startup, though the daemon's cached copy was already a weakness there. Round 1 refused the thread.
- **Fix, either:**
  - only skip enforcement for resume and fork when the target is `Embedded`; or
  - have app-server/daemon startup call `leave_default_login_unenforced()` when `named_accounts` is on. It never enforces anyway, and this also closes the cached-login gap. That changes how the standalone app server behaves, so it needs a product decision.
- **Also:** add a test or a documented scope.

## Nits
- **Remote workspace (`tui/src/lib.rs:1398-1405`):** remote resume now sets the flag locally. That's harmless because remote mode builds no local `shared_from_config` manager that sends requests. But the comment's "this process then never uses…" doesn't describe remote mode: the remote server decides. Either add `!uses_remote_workspace()` to the resume/fork arm or note it.
- **Stale reason (`login/src/auth/manager.rs:~3141-3155`, `clear_external_auth` `:3245`):**
  - The external-auth branch of `load_auth` and `clear_external_auth` don't refresh `hidden_default_login_reason`.
  - After a failed external resolution, `provider.rs:561-575` can refuse with an old "API key … left unchanged" reason instead of reporting "not signed in".
  - Clear the reason on those paths.
- **Duplicate read (`provider_accounts.rs:246`):** the thread-start check re-reads storage (a keychain read with keyring storage) on every thread and spawn in hiding processes. It could use `default_account_manager().hidden_default_login_reason()`, which is exactly what the provider would refuse with. Using it would also make the two checks agree when `CODEX_API_KEY` is set (the storage read uses `enable_codex_api_key_env=true`; the TUI manager uses `false`).
- **TUI resume/fork coverage:** only `exec` has an automated test. Make sure the true-TUI/SOP run covers `corbanu resume <named-id>` with `forced_login_method=chatgpt` and an API-key default (no onboarding, `auth.json` unchanged). Add `corbanu fork` for item 1.
- **`demo_video.py` `setup`:** fine. Index 0 doesn't collide with the 1-based step logs, and a failure raises before tmux starts.
