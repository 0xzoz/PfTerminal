## Finding 2 (remote app server): fixed, with caveats
- **At startup it works.** `lib.rs:1647` marks the session's own named OpenAI account as `Account`, and `metadata_for` now keeps that value when the local vault doesn't hold the account. So a remote session on `openai` with `--account openai:work` shows OpenAI configured again, both at startup and in the onboarding gate.
- **Caveat A: it doesn't survive a refresh.** Opening `/providers` or the shared setup screen calls `ProviderAccountMetadata::discover` (`provider_management_status.rs:142`, `event_dispatch.rs:2566`). That reads only the default login, and `update_account_metadata` writes the result into the same host that `/model` uses. In remote mode with no default login, `account.openai` drops to `Missing`, so OpenAI shows not configured again. This was also true before 064dad64b8, so it isn't a regression. It belongs in the remote-gap ticket, alongside the same issue for #417 API-key providers.
- **Caveat B: the new rule also matches the default login.** `account.openai == Account` doesn't only mean "startup checked the session's account". It is also the value when the default login is a ChatGPT login (`startup_provider.rs:91`, `discover`) or after `mark_openai_account`. So "default ChatGPT login present + named account not in the vault" still shows Configured.
  - Local sessions on that account are refused earlier by `session_account_error`.
  - What's left is sessions on another provider: `/model` shows OpenAI as configured, but using it is refused with the reason. The onboarding gate can also treat OpenAI as ready.
  - Before 064dad64b8 every case showed `Account`, so this isn't a regression either.
  - The new test labels its `Account` case as the session's checked account, but it would pass just as well for a default ChatGPT login.
  - A tighter fix for the follow-up: give the host an explicit "session account checked at startup" flag instead of reading it from `account.openai`, and have `discover` refreshes keep it.

## Finding 5: closed
Both cases are now tested: a default API-key login with an unenrolled named account gives NotConfigured, and `Account` with an unenrolled named account gives Configured. The case where a default ChatGPT login is present and the named account is unenrolled is ambiguous (caveat B), so it can't be tested yet. Leave it for the follow-up.
