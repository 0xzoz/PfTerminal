## Should-fix

**1. #570 is still open on resume and fork (high).**
- **What happens:** `corbanu resume <id>`, `corbanu fork <id>` or `corbanu exec resume <id>` on a thread recorded on a named account, started without `--account`, still logs out the default `auth.json` when the restrictions rule it out.
- **Why, in the TUI:** startup enforcement runs on the pre-resume config, which has no account (`tui/src/lib.rs:1392-1401`). The thread's recorded account is only applied afterwards (`tui/src/lib.rs:1681-1693`, `2010-2016`).
- **Why, in exec:** `inherited_provider_account` is `None` at `exec/src/lib.rs:514`, so enforcement at `exec/src/lib.rs:578-586` runs before `thread/resume`. The app server only applies the recorded account later (`thread_processor.rs:3698`).
- **Knock-on effect:** the in-process manager is built from that same initial config, so `hide_restricted_default_login` is false (`app-server/src/in_process.rs:425`).
- **Docs:** `docs/provider-accounts.md` now promises that a session on a named account "leaves the default login alone", which is false for this path.
- **Fix:** resolve the recorded account before enforcing, or defer enforcement until the thread's account is known. Add regression tests for resume and fork.

**2. The thread-start check is wider than its comment says (medium).**
- **Inaccurate comment:** `core/src/config/provider_accounts.rs:221-224` claims other sessions already log a ruled-out login out at startup. They don't in the standalone app server, the MCP server, or a TUI using a remote workspace. None of these call `enforce_login_restrictions`.
- **Behaviour change:** with `named_accounts` on, default OpenAI threads there are now refused (`thread_manager.rs:1855`). Before, they ran on that login. Stricter is arguably better, but it's a default-session change that nothing tests or documents.
- **Cost:** in TUI and exec default sessions the check is redundant, because startup enforcement already guarantees a compliant login. It still re-reads storage on every thread and spawned agent while a restriction is set; with keyring storage, that's a keychain read per spawn.
- **Fix:** gate the check on the thread's `auth_manager.default_account_manager()` actually hiding the default login (a small accessor). Otherwise, accept the change on purpose: fix the comment, document it and test it.

**3. Hiding depends on every manager being built from a config that carries the account (low, defence in depth).**
- The default login is no longer deleted in a named session, so safety now rests on `hide_restricted_default_login`. That is set only in `shared_from_config` and comes from whatever config is passed in.
- The app server's `load_latest_config` uses `ConfigOverrides::default()`, which drops `--account` (`config_manager.rs:143-160`). Managers built from such a config get `hide = false` and load the ruled-out login. Examples: `core/src/connectors.rs:205-207` and `chatgpt/src/connectors.rs`.
- Today these are only reached after gates that use the hidden shared manager (`apps_processor.rs:75-78`, `plugins.rs:1803-1806`), so nothing is sent. A future caller could slip past.
- **Fix:** add a comment or test pinning this invariant, or make hiding a process-level property.

**4. Missing regression tests.**
- **#571 end to end:** a Z.AI session with `--account openai:work` should send work's bearer token. The current test drives `TestAuthManagerConfig`, not the real `Config`.
- **TUI onboarding:** nothing tests that a named session skips the default-login screen (`tui/src/lib.rs:1717-1724`).
- **Reload:** nothing tests that a manager still hides the login after `reload()` or `reload_if_account_id_matches`. The new tests cover only construction and `auth()`.
- **Resume and fork:** see item 1.

## Nits
- **Custom providers:** `default_login_restriction_error` (`provider_accounts.rs:229-235`) also refuses a custom `requires_openai_auth` provider that has an `env_key`, which never uses the default login. Add `|| provider.env_key.is_some()`.
- **Mid-thread `/model` switch:** in a named-session process, switching to a provider on the default OpenAI login skips the thread-start check. The hidden login means the request goes out unauthenticated and gets a 401 instead of the clear refusal. Nothing leaks.
- **TUI bootstrap:** `stored_auth_has_codex_backend_auth` (`tui/src/app_server_session.rs:224-249`) reads the hidden `auth.json` directly. It can advertise backend features that the hidden manager then can't serve. No credential is sent.
- **Test temp dir:** `named_sign_in_tests.rs` uses `std::env::temp_dir()` plus the process ID and is left behind if the test panics. Use `tempdir()`.
- **Docs formatting:** `docs/provider-accounts.md:130` is an unwrapped long line.

## Your questions
1. **Security and policy.**
   - **Ruled-out login:** I found no path that sends a ruled-out default login.
     - Providers on the default login go through `default_account_manager()` (`model-provider/src/auth.rs:231-233`), so they get the hidden manager.
     - `account/read`, rate limits, the model list and the app/connector gates all use the hidden shared manager.
     - Spawned agents, resume and fork all go through `spawn_thread_with_source`.
     - The external ChatGPT tokens path is checked when the tokens are logged in.
   - **Named-account bypass:** named accounts can't bypass a restriction. `configured_forced_login_method` is exactly what the user configured; the effective value only adds an implied `api` for third-party providers, which have no OpenAI named accounts.
   - **Effective vs configured:** default-login flows still use the effective value: onboarding (`onboarding_screen.rs:222`), `cli/src/login.rs` and `account_processor`. The named-account sites use the configured value, which is correct. The base manager's `forced_login_method` field is only read for named accounts and for hiding, so the switch there is safe.
2. **Default sessions:** unchanged when the feature is off, because `provider.account` is only stamped when it's on. With the feature on, the TUI and exec still enforce at startup and log out or exit as before (cases 3, 4 and 6 test this). The exceptions are the extra per-thread read and the stricter refusals in standalone/remote app servers (item 2).
3. **`hide_restricted_default_login`:**
   - Applied on the initial load (after `forced_login_method` is set) and in `load_auth`, which covers reload and account-matched reload.
   - Named managers set it to false and are excluded explicitly.
   - The ephemeral store goes through `load_auth`, so it is filtered too.
   - External auth goes through `commit_external_auth` and `set_cached_auth` and is not filtered. That's acceptable because the app server validates it when it's logged in.
   - Refresh only operates on the cached (filtered) login.
4. **`api_auth` refusal:** I found no legitimate named path that gets refused.
   - OpenAI named accounts can't have `env_key`, `aws` or `auth` (`supports_named_accounts`), so the model key broker, environment keys, Bedrock and command auth never reach this branch.
   - Named API-key accounts return `Some`.
   - `Fatal` matches the existing `account_error` handling and stops pointless retries.
   - A login refused by the restrictions is reported through the `PermissionDenied` reason.
5. **Hint text:** accurate. `NamedLoginMethod` has Browser, DeviceCode and ApiKey variants, so "`corbanu login --account n` (add `--device-auth`)" is right. The docs are accurate apart from the resume gap.
6. **Tests:** each new test would fail without its fix.

   - If the manager used the effective value, the "implied" assert in `named_chatgpt_account_follows_only_the_configured_login_method` would fail.
