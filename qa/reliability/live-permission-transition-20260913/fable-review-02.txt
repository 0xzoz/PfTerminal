[P3] Thread is marked server-owned before the confirm request is even sent (unsupported path)
codex-rs/tui/src/app_server_session.rs:1250
`confirm_permissions` inserts the thread into `server_permission_threads` unconditionally, then returns `Unsupported` without sending anything when `thread_settings_update_supported == false`. From then on every `turn/start` for that thread omits `approval_policy`/`approvals_reviewer`/`sandbox_policy`/`permissions` (app_server_session.rs:1329-1339) even though no server-side settings operation was ever requested. On a legacy server that rejects `thread/settings/update`, the TUI previously could still change permissions via per-turn overrides; after a single popup selection it can no longer change them at all for that thread (no override on turn/start, no settings/update), and the only recovery is reconnecting. The guard exists to avoid replaying stale UI values after a real (possibly applied) request; it should only be set when a request is actually dispatched (i.e. inside the `supported` branch).

codex-rs/tui/src/chatwidget/settings.rs:11
`submit_user_message_with_history_and_shell_escape_policy` renders the user message into history before `submit_op` (`render_before_submit`). `defer_turn_for_permission_confirmation` then restores `safety_buffering_prompt` into the composer but does not remove/mark the already-rendered user cell. Low severity, but visible in the exact 'submit while confirmation pending' flow the contract asks to preserve.
