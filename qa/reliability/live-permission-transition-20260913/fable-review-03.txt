[P3] Unknown-unsupported confirm still marks thread server-owned and never downgrades capability
codex-rs/tui/src/app_server_session.rs:1249
V3 correctly skips `server_permission_threads.insert` when `thread_settings_update_supported` is already false. But the first confirm attempt against a server that rejects `thread/settings/update` (method-not-found / experimental gate) still inserts the thread before the reply, and the spawned task that learns `Unsupported` cannot clear the set or flip `thread_settings_update_supported` (only the legacy `thread_settings_update` path does). Scenario: older remote server, user opens /permissions first → thread marked server-owned, reply is Unsupported, config untouched (fine so far). Later a local-config path that still mutates TUI config and relies on OverrideTurnContext + per-turn `turn/start` overrides (e.g. the auto-review/feature toggle in config_persistence.rs ~655/1088) is used: the settings update is a silent no-op on that server, and `spawn_turn_start` now sends `approval_policy/permissions: None` for the marked thread, so the TUI displays settings Core never received. Before this patch the per-turn override kept those in sync on legacy servers. Smallest fix: on `PermissionConfirmationResult::Unsupported` in the `PermissionConfirmationCompleted` handler (which has `&mut AppServerSession`), remove the thread from `server_permission_threads` and/or set `thread_settings_update_supported = false`. Nonblocking; affects only servers without the experimental method.
