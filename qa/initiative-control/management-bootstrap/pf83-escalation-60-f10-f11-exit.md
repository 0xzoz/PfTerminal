## Picker and route navigation: what is native today

The TUI native fixtures can open permission/model pickers, render labels/current markers, send `KeyEvent` arrows and Enter within each popup, and inspect emitted exact provider/model and permission events. Key traversal is **per popup**: the picker-to-confirmation and picker-to-reasoning hops are re-injected by the fixture through popup-opening methods after reading emitted events, rather than driven end to end by keys. Of the nine reruns, **seven send keys at all**; `model_picker_same_slug_marks_only_exact_provider_current` is render-only, and `status_permissions_compact_next_turn_label_at_narrow_widths` is a status-label test. Those checks do **not** require a packaged binary or real inference. Existing fixtures below cover them; round 61 reran them in a focused lane instead of adding duplicate tests. Synthetic route identities qualify local UI identity/event plumbing only, not actual supported-route authority.

- `chatwidget::tests::permissions::permissions_selection_requests_full_access_after_consent` and `permissions_selection_requests_restriction_without_optimistic_mutation`: widget key events traverse the picker and, where applicable, the separately re-injected consent popup, emit the intended confirmation request and leave current permission config unchanged. `permissions_selection_requests_change_without_optimistic_history`, `permissions_selection_requests_confirmation_when_current_is_selected`, and `permissions_full_access_consent_does_not_claim_application` cover adjacent selection paths.
- `chatwidget::tests::popups_and_settings::model_picker_dismisses_after_selecting_openrouter_model_without_effort_choices`: Right/Down/Enter navigation, selected model event, fixture re-injection into the reasoning-popup method and dismissal. `model_picker_same_slug_marks_only_exact_provider_current`: only the exact provider/model pair is labeled current.
- `chatwidget::tests::custom_model_identity::custom_model_routes_are_distinguishable_before_selection`: two synthetic same-slug routes render distinct provider labels; Down/Enter selects `qa-b` and emits exact `OpenReasoningPopup`, `UpdateModelSelection` and `PersistModelSelection` provider/model values. Emitting the persist event is not proof of writing or restoring a real route.
- `app::permission_confirmation::tests` exercises embedded request/outcome correlation, refusal during pending confirmation, failure/uncertainty, saved-default nonmutation and stale completion handling. These are separate fixtures, not a single picker-to-real-route-to-command workflow.

A combined **synthetic** model-switch-while-permission-pending test is also expressible through these native widget/app events. It is not added here: existing tests already establish the local navigation claim under correction, while another synthetic combination would not satisfy F11's actual-route F03/F04/F05 requirement. That combined native race remains an admitted test gap, not a packaged-binary limitation. Likewise, native Escape/cancel traversal and a safe user-visible failure/retry sequence can be added; this revision does not claim them from success-path or injected-outcome tests.

Actual endpoint identity, successful inference/tool effects per exposed supported route, pending-switch behavior on those routes, and the complete human-observable workflow still need mediated inference and route receipts. They are not intrinsically impossible in a native integration harness: the current fixtures supply scripted inference, not that mediation. Independent exact-package real-key execution and evidence review remain the functional acceptance gate; a packaged binary alone supplies neither route mediation nor a pre-application barrier.
