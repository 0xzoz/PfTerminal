# PF-83 executor VM: survey result — usable machine, unusable account

The SSH key was authorised and the VM is reachable. The machine itself is
exactly what the gate needs; the **account** is not.

## The machine is right

- `Darwin 25.2.0`, `RELEASE_ARM64_VMAPPLE`, `VirtualMac2,1` — a genuine macOS
  guest on Apple Virtualization, not a container.
- `ProductVersion 26.2`, build `25C56`, arm64.
- 95 GiB volume, 17 GiB free.
- `sudo` requires a password (good).

This satisfies the "disposable macOS VM" half of the frozen requirement.

## The account is not

The supplied account is `neo2`, whose home is `/Users/neo_1`. It is a **used
account with live agent credentials**, not a clean synthetic executor identity.
Present in that home:

- `~/.codex/auth.json` — an agent credential file
- `~/.claude.json`, `~/.claude/`
- `~/.ssh/`, `~/.docker/`, `~/.config/`, `~/.agents/`, `~/.mcp.json`
- `~/.git` — a repository at the home root

The [isolated execution contract](../../code-blind-functional/isolated-execution.md)
is explicit that the executor gets **no user home, inherited secret environment
or credential files**, and that "a fresh account or Seatbelt policy alone is
insufficient". Running a code-blind executor as `neo2` would both violate the
contract and expose those credentials to the executor. No case was run.

Overriding `HOME` does not fix this. A process running as `neo2` can read
`/Users/neo_1` whatever `HOME` says, and enforcing filesystem denial needs
privileges this account does not have without a password.

## What would make it usable

A **fresh, empty account** on that same VM, used only by the executor:

- no `~/.codex`, `~/.claude*`, `~/.ssh`, `~/.docker`, `~/.agents`, `~/.mcp.json`
- not in the `admin` group (`neo2` currently is, so it can escalate with a password)
- the executor's SSH key authorised for it
- `tmux` available for the PTY driver (currently absent; `cargo`/`rustc` are also
  absent, which is fine because the package is shipped pre-built)

Creating an account needs administrative rights on the guest, which the manager
does not have and will not obtain through a password pasted into chat.

A second account `neo` already exists on the guest; it was not inspected and is
assumed to be personal rather than a synthetic test identity.

## Unrelated but worth knowing

The credentials sitting in `/Users/neo_1/.codex/auth.json` and `~/.claude.json`
are readable by anything running as that account. If the VM is meant to be a
throwaway test box, those should not be on it.

## Update — clean executor account provisioned

Travis created a dedicated account and it is correct:

- `agent`, uid 503, home `/Users/agent`, groups `staff, everyone, localaccounts,
  com.apple.access_ssh, …` — **not in `admin`**.
- Home contains only the macOS defaults plus `.ssh`. No `.codex`, `.claude*`,
  `.docker`, `.agents`, `.mcp.json`, no repository.
- `sudo` requires a password and the account cannot escalate.
- The executor SSH key authenticates.

The earlier `neo2` account is no longer in play.

## Control probes from inside `agent` — what is and is not enforced

Run read-only from the account itself, so these are observations, not the
authoritative preflight:

| Control | Result |
| --- | --- |
| Other users' credential files (`/Users/neo_1/.codex/auth.json`) | **denied** |
| Other users' home listing (`/Users/neo_1`, `/Users/neo`) | listable at top level (macOS default 755); contents denied |
| Corbanu source or checkout visible | none |
| Login keychain `Codex Auth` item | absent |
| Outbound internet (`https://github.com`) | **open — 200** |
| Guest → host TCP (`192.168.64.1:22`) | **open** |
| `tmux` | absent (needed for the PTY driver) |
| `cargo` / `rustc` | absent (fine; the package ships pre-built) |

Two controls the frozen gate requires are therefore **not** enforced yet:
unrestricted network egress, and the guest being able to reach the host. Neither
can be fixed from inside an unprivileged account — `pf` needs root — so they are
either a VM/network-level change or an explicitly recorded reduction in what the
gate establishes. Nothing was run against these gaps.

## Next technical step

The guest agent built in increment 3 targets the Docker diagnostic lane: it
expects `/state`, `/packet`, `/package`, `/runtime/guest.py` and `/denied/sockets`,
and `BoundaryWire` connects over a Unix socket. Driving this macOS VM over SSH
needs a native adapter, which is the next harness increment, followed by the
authoritative preflight run from inside the guest.
