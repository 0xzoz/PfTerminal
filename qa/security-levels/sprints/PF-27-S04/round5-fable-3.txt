[P2] 5s IO_DEADLINE applies to idle frame waits and receipt reads, tearing down healthy sessions
codex-rs/secret-broker/src/linux_transport.rs:29
`configure()` installs `IO_DEADLINE = 5s` as the socket read timeout on both ends. On the server, `serve_frames` -> `read_frame` blocks waiting for the *next* frame; any client idle >5s between dispatches yields a read timeout -> `SessionUnavailable` -> `CloseGuard::close()` -> `runtime.cancel_session`, destroying a valid registered generation with no disconnect having occurred (disconnect is already detected separately by the POLLRDHUP watcher). On the client, `LinuxBrokerChannel::dispatch` -> `read_receipt` waits for the broker's receipt, which arrives only after the backend completes the `POST /v1/responses` HTTP round trip; those routinely exceed 5s, so the client reports `OutcomeUnknown` and permanently closes the channel even though the broker completes the upload and journals `Completed`. Each such teardown forces a new `run_generation`, and `max_tracked_runs` (8 per session slot, non-evicting by design) is then exhausted by ordinary latency, producing `ResourceExhausted` until a broker restart. This is newly introduced code and contradicts the module's stated contract that only EOF/malformed/denial/timeout of a *frame* closes the generation. Smallest fix: apply the deadline only to mid-frame byte reads (e.g., set the timeout after the 4-byte prefix arrives and clear it before blocking for the next frame/receipt), or make the receipt wait unbounded/configurable while relying on the existing disconnect watcher for liveness.
