[P2] Stale-generation test asserts a kernel-version-specific SO_PEERPIDFD outcome
codex-rs/secret-broker-service/tests/support/children_tests.rs:235
`pf_27_s01_child_unknown_peer_and_old_generation_cannot_enter_replacement` reaps the old children (via `wait_for_shutdown`) and then requires `admit(old_stream)` to fail with `ErrorKind::ConnectionAborted`, i.e. the path where `getsockopt(SO_PEERPIDFD)` succeeds and the returned pidfd polls readable. That only happens on kernels that hand out pidfds for already-reaped `sk_peer_pid` (the 2025 pidfs/net change, ~6.16+). On 6.5–6.15 kernels (e.g. Ubuntu 24.04 GA/HWE) `SO_PEERPIDFD` for a reaped peer returns ENODATA/EINVAL, so `getsockopt(...)?` at children.rs:217 fails with an uncategorized `io::Error` and this assertion panics; on <6.5 it is ENOPROTOOPT. The security property is still fail-closed in all three cases, but the test as written is not portable and will fail the `--features synthetic-fixture` suite on common supported hosts, which undermines the evidence claim that this case is verified. Minimal fix: assert `is_err()` (the following successful `admit(new_stream) == Journal` already proves the slot was not consumed), or accept both the pre-match `getsockopt` error and `ConnectionAborted`, and note the kernel dependency in the evidence README.

overall: patch is correct (0.8)
The admission/lifetime seam is sound within its stated scope. SO_PEERPIDFD liveness precedes numeric PID/UID matching, and because the target Child is held unreaped by this object, an alive socket peer with an equal PID is necessarily that child; unsupported or reaped-peer kernels fail closed via the getsockopt error. Duplicate connections, parent socketpairs, wrong UIDs and unknown children are denied before slot consumption; a thread-spawn failure restores the Child and fences. Handlers run outside the control lock, panics are caught and still fence, fence() shuts down the retained channel clone and signals only pidfds, and the pre-reserved reaper means Drop/shutdown never create threads and never silently detach a Child. Cargo.lock/Bazel lock are consistent (rustix `process` already in the lockfile graph). The only actionable issue is a kernel-version-dependent assertion in the stale-generation test that will fail on 6.5–6.15 kernels despite the code itself denying correctly there.
