[P3] Pending-exit proof can fail closed on the expected owner-terminated denial log
codex-rs/tui/tests/suite/memory_human_fixture.rs:460
`failed` is set when the log contains `Phase 1 job failed for thread {source}:`. In the product, `job::run` calls `result::failed` for every `sample` error, including `StageOneMemoryDenial::OwnerTerminated` (memories/write/src/phase1.rs:272, core/src/memory_stage_one.rs:219-228). That denial is the *expected* consequence of the operator typing `/exit` while the canary response is pending; whether the warn line lands in `codex-tui.log` before the process exits is a race with TUI shutdown. When it does land, `is_pending()` rejects an exit that genuinely interrupted the pending job and the operator sees "job already failed; not exercised" for check 23. This is fail-closed (no false pass), so it is not a landing blocker, but it makes the manual pending-exit case spuriously non-passable on slower shutdowns. Smallest fix: exclude the `owner terminated` reason from the failure predicate (e.g. match `Phase 1 job failed for thread {source}:` only when the line does not end with `stage-one memory owner terminated`), keeping provider-change/other failures rejected.
