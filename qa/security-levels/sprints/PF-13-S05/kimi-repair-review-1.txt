## Findings

I found **no P1 and no new P2 defect** introduced by this delta. Two P3 items:

### P3-A — C2's thread-local suppression relies on hook-chaining for hooks installed after `install_panic_hook`; invariant is not asserted at `tui.rs`'s hook
- **File/line:** `codex-rs/tui/src/tui.rs:537`
- **Failure path:** `set_panic_hook` (installed after `install_panic_hook`) does not itself check `scoped_credential_callback_active()`; suppression of a secret-bearing panic payload depends on it chaining into the vault-aware hook and on no future hook formatting `info` before chaining. Today that chain is correct (it does not format), so this is **not** a reachable leak — it is an undocumented load-bearing invariant. If a later edit adds any `format!`/`tracing` of `panic_info` before `hook(panic_info)` in `tui.rs:539–541`, a scoped-callback panic could surface the secret.
- **Recommendation:** Add the same `scoped_credential_callback_active()` early-return (before any formatting) inside `set_panic_hook`, or add a comment there pinning the "check before format" invariant; ideally a subprocess test that installs a post-vault hook and asserts suppression.
- **Regression test:** Subprocess test that installs an additional hook after the vault hook and panics with a canary secret inside a scoped callback; assert the canary is absent from stderr/logs.
- **Confidence:** medium (invariant verified transitively today; risk is future regression, not current behavior).

### P3-B — Canary subprocess scan now enforces a 1 MiB ceiling but never *reduces* stored report size for legitimately large output
- **File/line:** `scripts/security_credential_canary.py:288–291`
- **Failure path:** Removing `bounded_output` means any probe whose combined stream exceeds 1 MiB now hard-fails qualification. That is the intended fail-closed behavior, but it converts a previously-passing verbose `--nocapture` transcript into a hard `QualificationError` with no opt-in truncation, so a noisy (but secret-free) dependency's future output could break the gate with a misleading "exceeds the capture limit" error rather than a clear "output too large to retain."
- **Recommendation:** Acceptable as-is (fail-closed is correct for a security gate); optionally include the measured byte count in the error so operators can distinguish "secret found" from "transcript too large."
- **Regression test:** Already covered by `test_run_command_capture_limit_is_utf8_bytes_and_fails_closed`.
- **Confidence:** high that behavior is intended; low severity.
